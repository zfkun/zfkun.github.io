写在前面

上一篇 《天猫魔盒2（TMB300A）固件提取与备份》 记录了怎么把原厂固件完整备份出来。备份是手段，不是目的。真正想做的事，是在这台老盒子上做点魔改：精简系统、去掉不需要的服务、尝试第三方固件，或者至少让它在一个可控的环境里跑起来。

但魔改之前，得先搞清楚它内部是怎么运转的。启动链怎么走、安全校验卡在哪、system 里哪些组件是厂商定制、哪些服务可以安全移除——这些不弄清楚，刷机就是碰运气。

这篇文章就是逆向分析阶段的记录。和上一篇一样，它会随分析进度逐步补充，不会一次写完。

最终实测结果: 签名校验拦截机制 不好处理， 就不进一步深究了 （浪费时间）

前置条件：

  • 完整的分区备份
  • TTL 串口访问
  • root shell

这三样在上一篇里已经齐了。

本文目标：

  • 还原完整启动链，确认每一级的输入输出；
  • 分析安全机制（Secure Boot、系统完整性校验）对魔改的实际约束；
  • 拆解 system 分区，定位厂商定制组件和可精简项；
  • 确认硬件驱动与内核模块的依赖关系，为第三方固件适配做准备。

边界：本文只做分析和记录，不涉及具体刷机操作。魔改实操留到下一篇。

4.1 分区表（U-Boot 视角）

Partition table get from SPL is :

   0: bootloader                         0            400000                  0
   1: reserved                     2400000           4000000                  0

与 Linux 下 /proc/partitions 的 mmcblk0p1~p10 完全对应，U-Boot 视角多了 offset 和 flag：

  • offset 是分区起始地址（十六进制）；
  • flag 可能与分区属性有关（如是否可启动、是否加密），具体含义需结合晶晨平台文档确认；
  • bootloader 之后到 reserved 之间有 32 MB 空隙，与 /proc/partitions 中总块数和分区块数合计的差值吻合。

4.2 环境变量分析

env.img 通过 strings 提取后，得到完整的 U-Boot 环境变量。以下是与魔改和安全相关的关键项。

💡 完整查看方法：strings env.img | head -100 只能看到前 100 行，可能截断长变量。建议用 strings env.img > env_full.txt 保存完整输出，再用 grep 按关键词筛选。

启动参数（bootargs）

将 initargs 与 storeargs 拼接，实际传给内核的 bootargs 为：

init=/init console=ttyS0,115200n8 no_console_suspend vmalloc=300m quiet
ramoops.mem_address=0x04e00000 ramoops.mem_size=0x100000
ramoops.record_size=0x8000 ramoops.console_size=0x10000 storage=2
vdaccfg=... logo=osd1,loaded,... hdmimode=1080p50hz cvbsmode=576cvbs
androidboot.firstboot=0 hdmitx=...

关键结论：

  • ❌ 没有 dm-verity / verify= 参数：内核未启用块设备级完整性校验；
  • ❌ 没有 androidboot.selinux=enforcing：SELinux 状态不由 bootargs 强制指定；
  • ❌ 没有 androidboot.verifiedbootstate=：未传递 Verified Boot 状态。

这意味着修改 system 分区后，内核层大概率不会因完整性校验而拒绝挂载。SysFileCheck 是用户空间的点名校验，不是 dm-verity。

启动流程（bootcmd / storeboot）

bootcmd=run storeboot
storeboot=echo enter storeboot...; echo Booting...; if unifykey get usid; then setenv bootargs ${initargs} androidboot.serialno=${usid}; fi; imgread kernel boot ${loadaddr}; setenv bootm_mode boot; bootm; run recovery1;
  • unifykey get usid 读取设备序列号，拼进 bootargs 的 androidboot.serialno=（原始值不展示）；
  • imgread kernel boot 读取 boot 分区并启动；
  • 启动失败时执行 recovery1（显示错误 logo，挂起）。

恢复与烧录通道

recovery_key=saradc open 0; if saradc get_in_range 0x0 0x50; then msleep 50; if saradc get_in_range 0x0 0x50; then setenv user_factoryreset true; save; run recovery; fi; fi
switch_bootmode=... if test ${reboot_mode} = factory_reset; then run recovery; ... usb_burning ... safe_mode ...
  • recovery_key 通过 SAR ADC 检测某个通道电压，连续两次命中触发恢复出厂；
  • reboot_mode 决定启动路径：正常、恢复出厂、OTA 更新、USB 烧录、安全模式；
  • usb_burning 和 sdc_burning 是两条救砖通道，具体触发方式待确认。

5.3 头地址与串口日志加载地址的差异

串口日志里：

Load Address: 00208000
Entry Point:  00208000
Ramdisk start addr = 0x12774800

而 bootimg 头里 kernel addr 是 0x10008000，ramdisk addr 是 0x11000000。

解释：U-Boot 读取 bootimg 后，会把 kernel 和 ramdisk 重定位到实际运行地址。头里的地址是 bootimg 打包时的约定地址，U-Boot 根据内存布局重新搬运。所以 0x10008000 → 0x00208000、0x11000000 → 0x12774800 是 U-Boot 的行为，不是镜像损坏。

5.4 binwalk 扫出的内容

binwalk 在 boot.img 中扫出大量：

  • ELF 32-bit LSB shared object, ARM：ramdisk 里的共享库和可执行文件；
  • Copyright string：大量 Android Open Source Project 和 IBM 的版权字符串；
  • WidevineMediaKit 路径：/var/lib/jenkins/workspace/Android_Classic_Widevine/...，说明 ramdisk 里包含 Widevine DRM 组件；
  • 蓝牙配置：/etc/bluetooth/bt_vendor.conf；
  • 证书：/etc/ssl/certs/ca-certificates.crt；
  • /usr/bin/ntlm_auth：网络认证工具。

💡 bix header、mcrypt 2.2 encrypted data 等大概率是误报或加密数据，不必过度解读。

结论：ramdisk 里不只有 init 脚本，还塞了不少厂商预置的二进制和库。

5.5 boot.img 内核与 ramdisk 数据疑似加密

abootimg -x 能正常解出 zImage、initrd.img、bootimg.cfg，但 zImage 前 512 字节全是随机字节，没有任何可读字符串：

00000000: 4d7a 6919 3461 6608 5ba2 114d c758 ee1b  Mzi.4af.[..M.X..
00000010: 0a56 3522 4c6f 5ddf f6e1 8d89 fda9 5565  .V5"Lo].......Ue
...

标准 uImage magic 是 27 05 19 56，gzip 是 1f 8b，ELF 是 7f 45 4c 46，前 512 字节里都没有出现。initrd.img 同样全是随机字节，file 返回 data，binwalk 无识别结果。

判断：boot.img 里的 kernel 和 ramdisk 数据很可能被 Amlogic 私有加密或加扰。bootimg.cfg 中的地址和大小与串口日志一致，说明 abootimg 切分偏移没错，只是内容不是明文。

keyIsBurned=0 只说明 efuse 中未烧录设备密钥，不代表镜像本身未加密——加密密钥可能硬编码在 BL1/U-Boot 中。

直接解包尝试结果：

  • Customization Tool 10.1.0 在部分 Windows 环境下启动闪退，无法使用。论坛中也有其他用户报告类似问题，换机器或换版本不一定能解决。
  • mkbootimg_tools 的 mkboot 脚本成功识别了 bootimg 头部（kernel 大小 7813310、ramdisk 大小 2604167、page size 2048 等），但最后报错 ramdisk is unknown format, can't unpack ramdisk。
  • 公开工具 abootimg、unpackbootimg、mkboot 均无法解包此 ramdisk，确认 Amlogic 对 ramdisk 数据做了私有封装或加密处理。

对魔改的影响：

  • 不能直接用标准 abootimg / unpackbootimg / mkboot 解包和重打包；
  • 不建议在逆向加密算法上投入过多时间，目标不是“解析原厂 ramdisk”，而是“让修改后的系统能启动”；
  • 更实际的路线是从运行系统重建 ramdisk。

5.6 second stage 实测结论与文件取舍

abootimg -i 报告的 second stage size = 2604167 与 ramdisk size 完全相同，这个值不可靠。实际提取结果：

工具 文件 大小 md5
abootimg -x stage2.img 42 KB ffa699b7bc23daec92da4765db819d90
mkboot second.img 42 KB ca930f1535689e9aada383cc2ec5372e
Python 按 42 KB 偏移切分 second_42k.bin 43008 字节 ca930f1535689e9aada383cc2ec5372e

mkboot 和 Python 切分结果完全一致，互相印证，说明 second 的真实大小是 43008 字节（42 KB），内容以这两个为准。abootimg 虽然也切出 42 KB，但内容不同，说明它对 Amlogic 私有 bootimg 的 second 偏移解析有偏差，stage2.img 不可用。

关于 mkboot 报错的说明：mkboot 解包时报告 ramdisk is unknown format, can't unpack ramdisk，这个错误发生在“尝试解压 ramdisk”阶段，不影响前面的“按 header 偏移切分 kernel、ramdisk、second”步骤。second.img 在报错之前就已经切好，且与 Python 按标准 bootimg 布局独立切出的结果 md5 完全一致，说明 mkboot 的 second 切分是正确的。

关于 second.img.tmp：mkboot 解包后会同时留下 second.img 和 second.img.tmp。.tmp 是工具“先写临时文件再改名”的中间产物，second.img 已正常生成，说明 second 切分完成。重打包用 second.img，不要用 .tmp。

second stage 只能从 boot.img 里切：second 区域不像 ramdisk 那样会在运行时解压挂载，内核启动时也没有使用它（/proc/cmdline 无相关参数，dmesg 只有 Freeing initrd memory），所以运行时无法导出 second，只能从原厂 boot.img 里按偏移切出。

5.7 从运行系统重建 ramdisk

原始 boot.img 中的 kernel 和 ramdisk 数据被 Amlogic 私有封装或加密，标准工具无法直接解包。但魔盒能正常启动，说明内核已经成功解压了 ramdisk，运行系统里的根文件系统就是 ramdisk 的内容。

重建 ramdisk 的完整流程如下。

前置确认

id
ls -la /init
ls -la /sbin
mount | grep -E '/system|/sbin|rootfs'

确认 root 权限、/init 是 ELF、/sbin 内容正常、rootfs 已挂载。

准备临时根目录

U 盘通常是 fuseblk（NTFS/exFAT），不支持符号链接，直接在 U 盘上 cp -a /sbin 会报 cp: symlink: ../init: Function not implemented。因此改为在 /data（ext4）下操作，最后只把生成的 cpio 文件复制到 U 盘：

rm -rf /data/local/rd_root
mkdir -p /data/local/rd_root
cd /data/local/rd_root

cp -f /init /init.rc /init.amlogic.rc /init.amlogic.board.rc /init.amlogic.usb.rc \
      /init.environ.rc /init.trace.rc /init.usb.rc /init.yunos.rc \
      /default.prop /file_contexts /file_manifest /file_whitelist \
      /property_contexts /restart_info.png /restore_info.rle . 2>&1

mkdir -p sbin
cd /sbin
find . \( -type f -o -type l \) | while read f; do
  mkdir -p "/data/local/rd_root/sbin/$(dirname "$f")"
  cp -a "$f" "/data/local/rd_root/sbin/$f" 2>/dev/null
done
ls -la /data/local/rd_root/sbin/

预期看到 adbd、alitvsecureboot、healthd，以及 ueventd -> ../init、watchdogd -> ../init 两个软链接。

一次性 cpio 打包

cd /data/local/rd_root
find . | cpio -o -H newc 2>/dev/null | gzip > /data/local/ramdisk_new.cpio.gz
ls -lh /data/local/ramdisk_new.cpio.gz

cp /data/local/ramdisk_new.cpio.gz /storage/external_storage/sda1/
ls -lh /storage/external_storage/sda1/ramdisk_new.cpio.gz

预期文件大小在 1–3 MB 量级，接近原厂 ramdisk 的 2.48 MB。

校验归档内容

gunzip -c /data/local/ramdisk_new.cpio.gz | cpio -it 2>/dev/null | grep sbin

预期看到 ./sbin/adbd、./sbin/alitvsecureboot、./sbin/healthd、./sbin/ueventd、./sbin/watchdogd。

拉到电脑

adb pull /storage/external_storage/sda1/ramdisk_new.cpio.gz

5.8 重打包 boot.img

用系统 apt 安装的 mkbootimg 重打包。注意 Debian 源里的 mkbootimg（29.0.6）使用 --base + --kernel_offset 风格，不支持直接指定 --kernel_addr 这类绝对地址：

mkbootimg \
  --kernel ~/boot_unpacked/zImage \
  --ramdisk /path/to/ramdisk_new.cpio.gz \
  --second ~/boot_mkboot/second.img \
  --base 0x10000000 \
  --kernel_offset 0x00008000 \
  --ramdisk_offset 0x01000000 \
  --second_offset 0x00f00000 \
  --tags_offset 0x00000100 \
  --pagesize 2048 \
  -o boot_new.img

生成后校验：

file boot_new.img
abootimg -i boot_new.img

file 应显示 Android bootimg，abootimg -i 里 kernel size 应为 7813310，ramdisk size 应与 ramdisk_new.cpio.gz 大小一致。

打包结果确认：boot_new.img 生成后，file 和 abootimg -i 输出如下：

boot_new.img: Android bootimg, kernel (0x10008000), ramdisk (0x11000000), second stage (0x10f00000), page size: 2048
  • kernel size 7813310，与原厂一致；
  • ramdisk size 1334740（约 1.27 MB），对应新生成的 ramdisk_new.cpio.gz；
  • abootimg -i 报告的 second stage size 1334740 是已知误读（把 ramdisk size 读成了 second size），实际 second 数据是打包时传入的 42 KB second.img。以 file 输出为准。

ramdisk 从原厂 2.48 MB 缩小到 1.27 MB，是正常现象：原厂 ramdisk 是加密/私有封装格式且包含 Widevine、蓝牙、证书等组件，新 ramdisk 只包含 init 脚本和 /sbin，标准 gzip cpio 压缩后体积更小。

工具职责区分：Debian apt 安装的 mkbootimg 只负责打包，不包含可用的解包功能。解包 boot.img 仍需使用 mkboot（mkbootimg_tools）或 abootimg。虽然 mkboot 解压 ramdisk 会报错，但它切分 kernel、second 的功能是正常的，且与 Python 独立切分结果一致。流程是：mkboot 解包 → 替换 ramdisk → mkbootimg 打包。

mkbootimg_tools 的兼容性：该工具目录下的 mkbootimg 是 2016 年编译的 32 位 x86 ELF 二进制，依赖 /lib/ld-linux.so.2。在 64 位 Debian 12 上直接执行会报“无法执行：找不到需要的文件”。如果确实要用，需先 sudo dpkg --add-architecture i386 && sudo apt install libc6:i386，但旧二进制对新版 glibc 的兼容性不保证。推荐直接使用系统 apt 安装的 mkbootimg（29.0.6）。
